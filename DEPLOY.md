# Розгортання

Сайт статичний — жодного бекенду. Тому хоститься безкоштовно, а «майже
реальний час» забезпечує cron у GitHub Actions.

## Крок 1. Репозиторій

```bash
cd tgmine
git init && git add -A && git commit -m "tgmine"
```

Створи на GitHub **порожній** репозиторій і підключи:

```bash
git remote add origin git@github.com:<твій-нік>/<назва>.git
git branch -M main && git push -u origin main
```

Перший коміт важить ~35 МБ (`data/` 15 МБ + `store/` 19 МБ). Газетир (132 МБ)
у `.gitignore` — CI тягне його сам і кешує.

**Публічний чи приватний.** Для публічного Actions безлімітні. Для приватного —
2000 безкоштовних хвилин на місяць (GitHub Free) або 3000 (Pro, $4/міс), і саме
це задає інтервал. GitHub округлює КОЖЕН прогін угору до хвилини, тому важлива
не сума секунд, а те, по який бік від 120 с лежить медіана.

**Прогін росте, і це головне число цього розділу.** Заміряно по API
(`run_duration_ms`, черга не рахується) 8 вересня 2026:

| крок | 25 липня | 6 вересня |
|---|---|---|
| checkout | 10 с | 22 с |
| тести на кроні | 4 с | 17 с |
| збірка сайту | 14 с | 27 с |
| збір постів | 19 с | 20 с |
| публікація | 15 с | 16 с |
| **разом** | **83 с** | **123 с** |

Тобто прогін перетнув 120 секунд і почав коштувати **3 білінгові хвилини
замість 2**. Спокійна доба (4–7 вересня, жодного пуша) виходила в 28 прогонів
і **79 хв/добу = 2373 хв/міс** — 119% безкоштовного Free.

Ростуть усі три доданки самі собою: checkout — від розміру репозиторію,
збірка сайту — від довжини архіву, тести — від їх кількості. Тому це не разова
поломка, а тренд: ~+10 с на місяць, тобто кожні півроку прогін дорожчає ще на
одну білінгову хвилину.

Що з цим зроблено 8 вересня 2026:

| правка | де | що дає |
|---|---|---|
| на кроні лишились тільки інваріанти сховища, а не пʼять модулів | `update.yml` | 17 с → 7 с |
| збірка сайту перестала розбирати кожну подію усьоме | `site.py` | 29 с → 19 с |
| `schedule` став ЗАПОБІЖНИКОМ-сторожем (job `clock`), а не четвертим повним прогоном | `update.yml` | 4 прогони × 3 хв → 4 × 1 хв |
| пуш більше не збирає пости й не комітить дані | `update.yml` | −26 с на прогін і мінус гонка за пуш у main |

**Заміряно на живому тіку годинника 8 вересня о 01:00 UTC: 105 с проти 128 с
напередодні** — тобто 2 білінгові хвилини замість 3. Кроки: checkout 22 с,
інваріанти 7 с, збір постів 20 с, збірка сайту 19 с, коміт 6 с, публікація
13 с.

Разом ≈ **52 хв/добу ≈ 1560 хв/міс**, тобто 78% Free (було 119%).

Запас — 15 секунд до наступної білінгової хвилини, і він не вічний. Прогін
гуляє на ±15 с від мережі (збір 20–23 с, публікація 11–16 с), а всі три
доданки й далі ростуть самі. Коли 105 с знову стане 120 — див. список нижче.

**Годину не можна зрізати наполовину, лишившись у безкоштовному.** Стеля — це
не інтервал, а округлення: будь-який прогін коштує щонайменше 1 хвилину, тож
2000 хвилин це 2000 прогонів на місяць = 66 на добу = раз на 22 хвилини навіть
за миттєвого job. При 129 с (3 хв) стеля — раз на 65 хвилин, тобто щогодинний
конвеєр уже впритул.

**Коли запасу не стане, вибір такий** (у порядку зростання роботи):

1. **GitHub Pro, $4/міс** — 3000 хвилин. Найдешевше в перерахунку на витрачений
   час і єдине, що не треба переробляти щопівроку.
2. Кешувати денні сторінки так само, як карти нальотів (−11 с). Ціна: числа для
   прози (`count_share`, `confirmed_share`) вшиваються в сторінку при збірці, і
   старі сторінки застигнуть зі своїми — тобто архів почне тихо розʼїжджатись
   у цифрах. Саме через це їх і перебудовують щоразу.
3. Збирати чотири канали паралельно (−7 с із 20 с збору). Чіпає єдиний
   незамінний крок конвеєра — тому не зроблено без потреби.

Репозиторій лишається приватним свідомо — не через координати (вони й так у
сайті), а тому що `configs/ru-monitor.yaml` містить точний перелік каналів і
всі регулярки. Конвеєр детермінований, тож видима методика дозволяє адресно
підсипати шум під патерни. Публічний репо зняв би ліміт хвилин, але відкрити
його означає й переписати історію: конфіг лежить у кожному з 500+ комітів,
інакше він засвітиться разом із ними. Ця ціна вища за $7/міс.

## Крок 2. Підключити Cloudflare Pages

Сайт роздає Cloudflare Pages, а не GitHub Pages: безкоштовний Pages працює лише
з публічного репозиторію (див. «Публікація вимкнена за замовчуванням»).

Проєкт створювати руками не треба — workflow робить це сам першим прогоном
(`wrangler pages project create`). Потрібні лише два значення з дашборда:

1. dash.cloudflare.com → права колонка будь-якої сторінки акаунта →
   скопіювати **Account ID**
2. Аватарка вгорі праворуч → My Profile → API Tokens → **Create Token** →
   шаблон **Edit Cloudflare Workers** (він включає право `Cloudflare Pages:
   Edit`). Токен показується один раз.
3. Покласти обидва значення плюс назву проєкту в секрети репозиторію. Токен
   вводити інтерактивно, не через `--body` і не через аргумент: інакше він
   осідає в історії shell.

```bash
gh secret set CLOUDFLARE_API_TOKEN
```

```bash
gh secret set CLOUDFLARE_ACCOUNT_ID
```

```bash
gh secret set CF_PAGES_PROJECT
```

`CF_PAGES_PROJECT` — назва проєкту, вона ж піддомен: `tgmine` дає
`tgmine.pages.dev`. Секрет, а не `vars`, лише заради однорідності з рештою: усі
три читаються тим самим `if`, і крок вмикається рівно тоді, коли покладено всі.

**Не підключай репозиторій до Cloudflare через Git** (Workers & Pages → Connect
to Git). Виглядає простіше, ламає дві речі. Перше: `site/` у `.gitignore`, тож
хостинг не знаходить що публікувати і роздає корінь репозиторію — сирі пости з
`data/` стають доступні по прямих шляхах, тобто приватність репозиторію
обходиться збоку. Друге: білд на кожен push, а бот комітить дані 24 рази на
добу — 500 безкоштовних білдів на місяць вичерпуються за три тижні. Готова тека
їде з Actions, де вже є Python, газетир і `store/`.

Direct Upload (те, що робить workflow) у квоту білдів не входить взагалі —
Cloudflare рахує лише збірки на своєму боці.

## Крок 3. Запустити

`Actions → update → Run workflow`

Далі само: щогодини збирає нові пости, перебудовує сайт, комітить дані
назад у репозиторій і публікує.

**Кеш браузера більше не тримає стару карту.** Скрипти редактора підключені
без версії в адресі (`labels.js`, `font.css`), і після оновлення браузер
показував попередню збірку: оператор бачив ті самі підписи, які щойно
прибрали, і питав, чи взагалі задеплоїлось. Тепер збірка сама дописує до
кожного посилання короткий хеш ВМІСТУ (`labels.js?v=0e771ede`) — адреса
міняється рівно тоді, коли міняється файл. Поруч кладеться `_headers`:
HTML не кешується взагалі, скрипти й стилі — назавжди, бо їх адреса вже
несе версію.

Локальний `mapper/run.sh` віддає все з `Cache-Control: no-store` — там
файли правляться щохвилини, і кеш заважає більше, ніж допомагає.

Сайт буде на `https://<назва-проєкту>.pages.dev/`, а редактор карт — на
`https://<назва-проєкту>.pages.dev/mapper/editor.html`: `site.py` копіює
теку `mapper/` у збірку разом із підкладкою, шрифтом і кешем плиток
(19 МБ, заливається раз — далі хостинг вантажить лише змінене)

## Як перевірити, що годинник живий

```bash
gh run list --limit 40 --json event -q '[.[].event] | group_by(.) | map({event: .[0], n: length})'
```

Якщо серед подій НЕМА `workflow_dispatch` — Worker не стріляє (не розгорнутий,
протух токен або впав), і конвеєр живе лише на `schedule`, тобто на черзі
GitHub. Виміряно 1 вересня 2026: за добу 5 запусків `schedule` замість 24, з
них 2 впали на пуші даних. Свіжість у такому режимі — 5-6 годин, а не година.

Те саме питає й сам workflow. З 8 вересня 2026 у нього два job-и: `clock`
запускається ТІЛЬКИ на `schedule`, питає GitHub про останній
`workflow_dispatch` і вирішує, чи потрібен повний прогін:

* тік свіжіший за 90 хвилин і закінчився добре → `go=false`, `build`
  пропускається, запобіжник коштує 1 білінгову хвилину замість 3;
* тіку нема, він старший за 90 хвилин або останній прогін годинника впав →
  `go=true`, далі все як завжди.

Будь-яка помилка самої перевірки (не відповів API, збилась дата, впав job)
трактується як `go=true`. Тихо пропустити запобіжник страшніше за дві зайві
хвилини. Тому ж перевіряється не лише ЧАС останнього тіку, а і його
ПІДСУМОК: інакше конвеєр, що падає щогодини, виглядав би для запобіжника
живим, і GitHub перестав би слати листа про збій розкладу — єдине
повідомлення, яке приходить саме.

Ознака в інтерфейсі: у прогоні на `schedule` видно один короткий job `clock`
із рядком «годинник живий — повний прогін не потрібен», а `build` сірий,
пропущений. Це НОРМА, а не збій.

## Крок 4. Детермінований годинник (`cron/`)

Крон у GitHub Actions — не розклад, а побажання. Подія `schedule` потрапляє в
чергу, яку GitHub розгрібає за залишковим принципом і під навантаженням
частково відкидає. Виміряно тут за 5 діб:

| | заявлено | фактично |
|---|---|---|
| прогонів/добу | 24 | **11.6** |
| медіанний інтервал | 60 хв | **121 хв** |
| максимальний | — | **238 хв** |

Тобто «щогодини» насправді означало раз на дві години, а іноді раз на чотири.
Це б'є не лише по свіжості: сторінка «Що зараз» вважає дані застарілими після
120 хвилин, а при медіані 121 попередження горіло приблизно половину часу й
привчало читача його ігнорувати.

`workflow_dispatch` через API такої черги не має. Тому розклад винесено у
Worker на Cloudflare, а в `update.yml` `schedule` лишається запобіжником раз на
6 годин — на випадок, якщо Worker помре.

Потрібен окремий токен GitHub (не той, що для Cloudflare):

1. github.com → Settings → Developer settings → Personal access tokens →
   **Fine-grained tokens** → Generate new token
2. Repository access → Only select repositories → `tgmine`
3. Permissions → Repository permissions → **Actions: Read and write**
4. Термін дії — на скільки готовий; після протухання конвеєр стане, і побачиш
   це лише за тим, що сайт не оновлюється

```bash
cd cron && npx --yes wrangler@4 login
```

```bash
cd cron && npx --yes wrangler@4 secret put GH_TOKEN
```

```bash
cd cron && npx --yes wrangler@4 deploy
```

`wrangler login` відкриє браузер — токен Cloudflare тут не потрібен.

**`secret put` не замінює `deploy`.** На порожньому акаунті друга команда
спитає «There doesn't seem to be a Worker called "tgmine-cron". Do you want to
create a new Worker with that name?» — і на Y створить ЗАГОТОВКУ: ім'я є,
секрет усередині є, коду й крону нема. Виглядає як успіх, а годинник мовчить.
Третю команду треба виконати обов'язково, вона й заливає `src/index.js` разом
із тригером. Ознака справжнього деплою у виводі — рядок `schedule: 0 * * * *`.

Вимкнені `workers_dev` і `preview_urls` у `wrangler.toml` — не прикраса: без
них wrangler за замовчуванням видає Worker публічну адресу
`tgmine-cron.<акаунт>.workers.dev`. Обробника `fetch` тут нема, тож вона
віддає 500 (error code 1101) і смикнути конвеєр через неї не можна — але це
зайва поверхня на скрипті, що тримає токен GitHub із правом запису в Actions.

Перевірити, що годинник цокає: dash → Workers & Pages → `tgmine-cron` →
Logs, або просто глянути, чи прогони в Actions пішли рівно о :00:

```bash
gh run list --limit 40 --json event,createdAt -q '.[] | "\(.createdAt) \(.event)"'
```

Заміряно після першого деплою 1 вересня 2026: тік о 14:00:27 UTC, тобто
затримка Worker → GitHub близько півхвилини.

## Що робить workflow

0. На `schedule` — спершу job `clock`: чи живий Worker (див. вище). Живий —
   решта не робиться зовсім
1. Кешує газетир (GeoNames + Natural Earth) — тягне лише перший раз
2. `sync.py --since 2d` — доваантажує нові пости, розбирає у сховище.
   **На пуш не робиться**: пости приносить годинник, а не правка коду
3. `site.py --raids --raid-days 2` — зведення й денні сторінки за ВСІ доби,
   карти нальотів лише за свіжі (решта з кешу)
4. Комітить `data/` і `store/` назад — дані накопичуються в репозиторії.
   **На пуш не робиться**: нема чого комітити, а спроба створювала гонку за
   пуш у main між ботом і людиною
5. Заливає `site/` на Cloudflare Pages (`wrangler pages deploy site`)

Тести: на пуш — повний набір, на кроні — лише інваріанти вже зібраного
сховища (`TestStoreInvariants`, `TestNearNeedsARealCoordinate`). Причина в
`update.yml` біля кроку: між тіками годинника не міняється ні код, ні версії
залежностей, тож решта тестів може тільки повторити відповідь останнього
зеленого пуша. Міняється саме сховище — його й перевіряємо.

Заливка інкрементальна: wrangler хешує файли й шле лише змінені. Тому вся
економія байтів нижче (карти з кешу, жар раз на добу) працює й тут — незмінені
файли по мережі не йдуть узагалі.

**Cloudflare ріже `.html` з адрес, і це не вимикається.** `/nights.html` віддає
308 на `/nights`, `/day/2026-04-18.html` — на `/day/2026-04-18`. Сайт генерує
посилання з розширенням (щоб працював локальний `python3 -m http.server`), тож
кожен внутрішній перехід коштує зайвий хоп до крайового вузла. Це не поломка:
цілі віддають 200, відносні шляхи всередині сторінок резолвляться так само
(база в `/day/` лишається `/day/`), `.json` не чіпається взагалі. Прибрати можна
лише переїздом на Workers Static Assets (`html_handling: "none"`) або
генерацією посилань без розширення — і те, і те дорожче за один 308.

## Чому карти нальотів кешуються

Денні сторінки за всі 93 доби будуються 6 секунд. Карти нальотів до тих самих
діб — 5.5 хвилини й 53 МБ, тобто 99% часу і 95% ваги сайту.

Раніше це «економилось» через `--days 10`, і сайт показував 10 діб із 93 —
різалось дешеве заради дорогого. Тепер карти переїжджають між прогонами кешем
(`actions/cache`, ключ на добу), а `--raid-days 2` перебудовує лише ті ночі,
дані по яких ще доходять. Крок збірки сайту — 16-18 с при теплому кеші проти
268 с на холодному, архів при цьому повний.

**Restore і save рознесені на два кроки навмисно.** `actions/cache` одним
кроком зберігає кеш у post-дії, а вона не зберігає нічого, якщо job впав.
Спостережено тут 20-24 липня: публікація почала падати на 403 → кеш карт не
осідав → наступний прогін будував усі 98 діб з нуля → знову падав → знову не
зберігав. Медіана прогону 1.8 хв стала 8.5, тобто ~3100 хв/міс проти 2000
безкоштовних, і помітити це можна було лише в білінгу. Окремий `cache/save` з
`always()` одразу після збірки сайту розриває цей звʼязок: поломка публікації
більше не робить наступні прогони холодними.

**Кеш тут не оптимізація, а умова коректності.** `wrangler pages deploy site`
публікує рівно вміст теки: без відновлених карт кожен прогін зносив би з сайту
весь архів, лишаючи останні дві ночі.

Якщо кеш колись загубиться, найближчий прогін відбудує всі карти з нуля — це
~5.5 хвилини, вкладається у `timeout-minutes: 20`.

## Публікація вимкнена за замовчуванням

Крок публікації сам вимикається, доки нема секретів `CLOUDFLARE_API_TOKEN`,
`CLOUDFLARE_ACCOUNT_ID` і `CF_PAGES_PROJECT`, і вмикається тієї ж миті, коли
вони зʼявляться — окремого перемикача нема навмисно. Забутий перемикач при вже
покладеному токені виглядав би точнісінько як робочий конвеєр, що мовчки нічого
не публікує.

Доки секретів нема, cron збирає дані й будує сайт у `site/`, але нікуди його не
відправляє, лишає в логах `::notice::` з поясненням і завершується зеленим. Це
навмисно: інакше кожен із 24 щоденних запусків був би червоним, і справжній
збій загубився б серед них.

**Чому не GitHub Pages.** Безкоштовний Pages роздає лише з публічного
репозиторію — на приватному `configure-pages` падає з «Get Pages site failed».
Зробити репозиторій публічним можна, і тоді Pages працює без жодних токенів,
але публічними стають і база військових обʼєктів із координатами, і зібрані
пости, і логіка відбору в `configs/`. Cloudflare роздає сайт із приватного
репозиторію, тому вибрано його.

## Як помітити, що збір зупинився

Тихий збій тут небезпечніший за гучний: сайт лишається на місці, просто перестає
оновлюватись.

**Що вже сигналізує само:**

- Сторінка «Що зараз» рахує вік даних і після 2 годин пише «оновлення
  затрималось» помаранчевим (`site.py`, `stale = age>120`). Поріг тримати
  прив'язаним до крону: при годинному інтервалі й типовому запізненні GitHub
  на десятки хвилин менше значення стояло б майже завжди. Це видно читачеві,
  не лише власнику.
- GitHub надсилає лист про невдалий запуск за розкладом — на адресу того, хто
  востаннє змінював workflow.

**Чого ніщо не покаже:**

- **Заплановані workflow вимикаються самі після 60 днів без активності в
  репозиторії.** Бот комітить дані щопівгодини, і зазвичай це зараховується як
  активність, але покладатись на це не варто: раз на кілька тижнів варто
  зазирнути у вкладку Actions.
- Крок збору обмежений 20 хвилинами (`timeout-minutes`). Якщо він почне
  впиратись у ліміт, у логах буде обрив, а даних за ту добу — менше.
- Мовчазне порожнє повернення `t.me/s/` виглядає як «тиха ніч». Розрізнити можна
  лише за тим, що всі три канали замовкли одночасно.

## Альтернативи хостингу

Cron у будь-якому разі лишається в Actions — жоден із хостингів не вміє
збирати дані, лише роздавати готову теку.

| | Плюс | Мінус |
|---|---|---|
| **Cloudflare Pages** (обрано) | приватний репо, трафік необмежений, Direct Upload поза квотою білдів | 3 секрети замість 2 |
| Netlify | приватний репо, заливка теки одним рядком | 100 ГБ/міс трафіку |
| GitHub Pages | нуль токенів, нуль сторонніх акаунтів | лише з публічного репозиторію |

Обрано Cloudflare, бо квоти обох безкоштовних планів упираються саме в те, що
робить цей конвеєр. У Netlify це трафік: 100 ГБ/міс при сайті на 56 МБ. Впертись
складно (читач тягне одну сторінку, а не архів — рахувати треба по візитах, не
по вазі теки), але стеля існує. У Cloudflare трафік не лімітований узагалі.

Друге — частота публікацій. 24 деплої на добу це ~720 на місяць при
безкоштовних 500 білдах. Пастка в тому, що на обох хостингах ліміт рахує СВОЇ
збірки, а не заливки: тут тека приїжджає готовою з Actions, тож у квоту не
потрапляє ні там, ні там. Але це вірно рівно доти, доки репозиторій НЕ
підключений через Git — див. Крок 2.

Розміри з великим запасом: 20 000 файлів на проєкт при 197 наявних, 25 МіБ на
файл при найбільшому 0.8 МБ (`targets.json`).

Cloudflare зараз штовхає нові проєкти на Workers Static Assets замість Pages.
Для чистої статики з Direct Upload різниці нема, Pages простіший; переїзд має
сенс лише якщо колись знадобиться щось серверне поруч із сайтом.

## Важливо про дані

`data/` — сирі пости з Telegram. Це **єдина річ, яку не можна відновити**:
веб-превʼю `t.me/s/` віддає лише обмежену глибину історії. Похідний шар
(`store/`) перебудовується будь-коли командою `python3 sync.py --rebuild`.

Тому `data/` комітиться в репозиторій навмисно, попри розмір.

### Репозиторій росте в 25 разів швидше за дані

Заміряно 8 вересня 2026:

| | |
|---|---|
| вміст `data/` + `store/` у робочій копії | 202 МБ |
| приріст вмісту | **2.3 МБ/добу** (не 0.5, як тут стояло) |
| розмір репозиторію на GitHub | **3.18 ГБ** за 51 добу |
| приріст репозиторію | **60–100 МБ/добу** |
| стеля, після якої GitHub пише листа й може заблокувати пуш | 5 ГБ |
| **запас** | **≈ місяць** |

Різниця між 2.3 і 64 МБ на добу — не дані, а пакування. Бот комітить
щогодини, і кожен коміт кладе в історію нову версію файла на 32 МБ:
`data/lpr1_treugolnik.jsonl` має в історії **960 версій**, які зараз займають
**1.69 ГБ**. При цьому файл дописується по 21 рядку за прогін — тобто дельта
мала б бути мізерною. Перевірено: 246 версій цього файла, спаковані окремо
(`git pack-objects --window=50`), важать **3.9 МБ**, по 16 КБ на версію. У
спільному паку git цих дельт не знаходить, і GitHub своїм gc — теж.

**Щогодинний коміт при цьому не зайвий.** Він не «зберігає дані частіше»,
він звужує вікно втрати: канали моніторингу видаляють і правлять пости, а
`t.me/s/` віддає лише те, що зараз висить. Комітити раз на добу означає
погодитись, що пост, який зʼявився о 01:05 і зник о 01:50, не потрапить у
архів ніколи. Тому міняти треба не частоту, а ціну коміту.

Що з цим можна зробити, у порядку зростання ризику:

1. **Переписати історію разово** (`git filter-repo` по `data/**` + force-push).
   Історія цих файлів безсенсова: вони тільки дописуються, значення має лише
   остання версія. Дає 3.2 ГБ → сотні мегабайтів. Робити ТІЛЬКИ із зупиненим
   кроном: бот пушить щогодини, і force-push у гонці з ним втратить коміт.
2. **Розкласти сирі пости по місяцях** (`data/<канал>/2026-09.jsonl`). Коміт
   тоді переписує лише поточний місяць, а не всю історію каналу; місяць
   закінчився — файл більше не міняється ніколи. Чіпає незамінний шар, тож
   потребує окремої роботи з тестами.
3. **Окрема гілка під дані, яку щоразу перезаписують одним комітом.** Історії
   нема взагалі, розмір виходить на плато. Найризикованіше: force-push у гонці
   з ботом.

### Сховище й сирий шар розійшлись у глибині

`data/` містить пости з **2025-11-15**, а `store/events/` — лише з
**2026-04-18** (144 доби проти 298). Тобто `sync.py --rebuild` на чистій
машині збудує сховище ВДВІЧІ глибше за те, що в репозиторії, і сайт
самопливом отримає 154 нові доби архіву.

Це не поломка, але й не рішення — просто наслідок того, що сирий шар колись
догребли вглиб без перебудови похідного. Поки воно так, `store/` не можна
виносити з репозиторію в кеш: перший же промах кеша тихо подвоїть архів на
сайті. Спершу треба вирішити, з якої дати сайт узагалі має починатись, і
зафіксувати це явно.

## Злиття локальних запусків із прогонами бота

Крон пише в `data/` і `store/` щогодини. Якщо ти теж щось ганяв локально, при
`git pull` буде конфлікт — це норма, а не аварія.

**Не знімай його через `git checkout --ours` чи `--theirs`.** Обидві сторони
містять пости, яких нема в іншої, і вибір однієї знищує решту назавжди:
`t.me/s/` віддає обмежену глибину історії. Втрата мовчазна — файл валідний,
конвеєр працює, подій просто нема.

Замість цього один раз у клоні:

```bash
python3 mergejsonl.py --install
```

Далі `git pull` просто працює: сирі пости обʼєднуються за `id`, події за `id`
зі збереженням часового порядку, курсори в `state.json` беруться максимальні.

`git clone` цього НЕ переносить — `.gitattributes` їде з репозиторієм, а сам
драйвер живе в локальному `.git/config`. Доки не ввімкнено, Git конфліктує як
завжди, тобто мовчазної втрати не буде в жодному разі.

Після злиття похідний шар варто вирівняти: `python3 sync.py --rebuild`.

## Локальний запуск

```bash
pip3 install -r requirements.txt
python3 sync.py --rebuild        # зібрати сховище з наявного кешу
python3 site.py --raids          # згенерувати сайт
python3 -m http.server -d site 8000
```
