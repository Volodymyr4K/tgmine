# Розгортання

Сайт статичний — жодного бекенду. Тому хоститься безкоштовно, а «майже
реальний час» забезпечує cron у GitHub Actions.

## Крок 1. Репозиторій

```bash
cd tgmine
git init && git add -A && git commit -m "tgmine"
```

Створи на GitHub **порожній** репозиторій і підключи:

```bash
git remote add origin git@github.com:<твій-нік>/<назва>.git
git branch -M main && git push -u origin main
```

Перший коміт важить ~35 МБ (`data/` 15 МБ + `store/` 19 МБ). Газетир (132 МБ)
у `.gitignore` — CI тягне його сам і кешує.

**Публічний чи приватний.** Для публічного Actions безлімітні. Для приватного —
2000 безкоштовних хвилин на місяць, і саме це задає інтервал крону. Прогін
триває 1м22с, але GitHub округлює вгору до хвилини, тобто рахує 2 хв:

| cron | запусків/добу | хв/міс | |
|---|---|---|---|
| 30 хв | 48 | ~2980 | перебір ~1000 хв ≈ $8/міс |
| 45 хв | 32 | ~1980 | впритул, нуль запасу на ручні прогони |
| **година** (обрано) | 24 | ~1490 | 74% ліміту |
| 2 години | 12 | ~745 | 37% |

Репозиторій лишається приватним свідомо — не через координати (вони й так у
сайті), а тому що `configs/ru-monitor.yaml` містить точний перелік каналів і
всі регулярки. Конвеєр детермінований, тож видима методика дозволяє адресно
підсипати шум під патерни. Публічний репо зняв би ліміт хвилин, але ця ціна
вища за $8/міс.

## Крок 2. Підключити Netlify

Сайт роздає Netlify, а не GitHub Pages: безкоштовний Pages працює лише з
публічного репозиторію (див. «Публікація вимкнена за замовчуванням»).

Netlify перейменував Sites на Projects, тому в інтерфейсі «Site ID» зветься
«Project ID» — значення те саме.

1. netlify.com → створити проєкт через **Deploy manually** (перетягнути теку
   `site`). Саме manual, не через Git — чому, нижче.
2. Project configuration → Project information → скопіювати **Project ID**
3. Аватарка внизу ліворуч → User settings → Applications →
   Personal access tokens → **New access token** (показується один раз)
4. Покласти обидва значення в секрети репозиторію. Токен вводити інтерактивно,
   не через `--body` і не через аргумент: інакше він осідає в історії shell.

```bash
gh secret set NETLIFY_AUTH_TOKEN
gh secret set NETLIFY_SITE_ID
```

**Не підключай репозиторій до Netlify через Git.** Виглядає простіше, ламає дві
речі. Перше: `site/` у `.gitignore`, тож Netlify не знаходить що публікувати і
роздає корінь репозиторію — сирі пости з `data/` стають доступні по прямих
шляхах, тобто приватність репозиторію обходиться збоку. Друге: білд на кожен
push, а бот комітить дані 24 рази на добу — 300 безкоштовних хвилин збірки
вичерпуються за кілька днів. Готова тека їде з Actions, де вже є Python,
газетир і `store/`.

Якщо репозиторій уже був підключений: Build & deploy → Continuous deployment →
**Unlink repository**, потім Deploys → **Unpublish** на активному деплої.

## Крок 3. Запустити

`Actions → update → Run workflow`

Далі само: щогодини збирає нові пости, перебудовує сайт, комітить дані
назад у репозиторій і публікує.

Сайт буде на `https://<назва-сайту>.netlify.app/`

## Що робить workflow

1. Кешує газетир (GeoNames + Natural Earth) — тягне лише перший раз
2. `sync.py --since 2d` — доваантажує нові пости, розбирає у сховище
3. `site.py --raids --raid-days 2` — зведення й денні сторінки за ВСІ доби,
   карти нальотів лише за свіжі (решта з кешу)
4. Комітить `data/` і `store/` назад — дані накопичуються в репозиторії
5. Заливає `site/` на Netlify (`netlify-cli deploy --prod --dir=site`)

Прапорця `--no-build` не існує — `deploy` і так нічого не збирає, збірку
вмикає лише явний `--build`.

## Чому карти нальотів кешуються

Денні сторінки за всі 93 доби будуються 6 секунд. Карти нальотів до тих самих
діб — 5.5 хвилини й 53 МБ, тобто 99% часу і 95% ваги сайту.

Раніше це «економилось» через `--days 10`, і сайт показував 10 діб із 93 —
різалось дешеве заради дорогого. Тепер карти переїжджають між прогонами кешем
(`actions/cache`, ключ на добу), а `--raid-days 2` перебудовує лише ті ночі,
дані по яких ще доходять. Прогін із 28 с став 13 с, архів при цьому повний.

**Кеш тут не оптимізація, а умова коректності.** `netlify deploy --dir=site`
публікує рівно вміст теки: без відновлених карт кожен прогін зносив би з сайту
весь архів, лишаючи останні дві ночі.

Якщо кеш колись загубиться, найближчий прогін відбудує всі карти з нуля — це
~5.5 хвилини, вкладається у `timeout-minutes: 20`.

## Публікація вимкнена за замовчуванням

Крок публікації сам вимикається, доки нема секретів `NETLIFY_AUTH_TOKEN` і
`NETLIFY_SITE_ID`, і вмикається тієї ж миті, коли вони зʼявляться — окремого
перемикача нема навмисно. Забутий перемикач при вже покладеному токені виглядав
би точнісінько як робочий конвеєр, що мовчки нічого не публікує.

Доки секретів нема, cron збирає дані й будує сайт у `site/`, але нікуди його не
відправляє, лишає в логах `::notice::` з поясненням і завершується зеленим. Це
навмисно: інакше кожен із 24 щоденних запусків був би червоним, і справжній
збій загубився б серед них.

**Чому не GitHub Pages.** Безкоштовний Pages роздає лише з публічного
репозиторію — на приватному `configure-pages` падає з «Get Pages site failed».
Зробити репозиторій публічним можна, і тоді Pages працює без жодних токенів,
але публічними стають і база військових обʼєктів із координатами, і зібрані
пости, і логіка відбору в `configs/`. Netlify роздає сайт із приватного
репозиторію, тому вибрано його.

## Як помітити, що збір зупинився

Тихий збій тут небезпечніший за гучний: сайт лишається на місці, просто перестає
оновлюватись.

**Що вже сигналізує само:**

- Сторінка «Що зараз» рахує вік даних і після 2 годин пише «оновлення
  затрималось» помаранчевим (`site.py`, `stale = age>120`). Поріг тримати
  прив'язаним до крону: при годинному інтервалі й типовому запізненні GitHub
  на десятки хвилин менше значення стояло б майже завжди. Це видно читачеві,
  не лише власнику.
- GitHub надсилає лист про невдалий запуск за розкладом — на адресу того, хто
  востаннє змінював workflow.

**Чого ніщо не покаже:**

- **Заплановані workflow вимикаються самі після 60 днів без активності в
  репозиторії.** Бот комітить дані щопівгодини, і зазвичай це зараховується як
  активність, але покладатись на це не варто: раз на кілька тижнів варто
  зазирнути у вкладку Actions.
- Крок збору обмежений 20 хвилинами (`timeout-minutes`). Якщо він почне
  впиратись у ліміт, у логах буде обрив, а даних за ту добу — менше.
- Мовчазне порожнє повернення `t.me/s/` виглядає як «тиха ніч». Розрізнити можна
  лише за тим, що всі три канали замовкли одночасно.

## Альтернативи хостингу

Cron у будь-якому разі лишається в Actions — жоден із хостингів не вміє
збирати дані, лише роздавати готову теку.

| | Плюс | Мінус |
|---|---|---|
| **Netlify** (обрано) | приватний репо, 2 секрети, заливка теки одним рядком | 100 ГБ/міс трафіку |
| Cloudflare Pages | приватний репо, трафік необмежений | треба шукати Account ID у дашборді |
| GitHub Pages | нуль токенів, нуль сторонніх акаунтів | лише з публічного репозиторію |

300 безкоштовних хвилин збірки Netlify тут не витрачаються: `deploy` без
`--build` лише заливає готові файли, збірка йде в Actions. Ліміт, у який реально
можна впертись — 100 ГБ трафіку на місяць. Сайт важить 56 МБ, але 53 з них це
карти нальотів: читач тягне одну сторінку, а не архів, тож рахувати треба по
візитах, не по вазі теки.

Перехід на Cloudflare — заміна одного кроку в `update.yml` на
`cloudflare/wrangler-action` з `pages deploy site`.

## Важливо про дані

`data/` — сирі пости з Telegram. Це **єдина річ, яку не можна відновити**:
веб-превʼю `t.me/s/` віддає лише обмежену глибину історії. Похідний шар
(`store/`) перебудовується будь-коли командою `python3 sync.py --rebuild`.

Тому `data/` комітиться в репозиторій навмисно, попри розмір. Зростання
приблизно 0.5 МБ на добу — на рік це ~200 МБ, у ліміти GitHub вкладається.

## Злиття локальних запусків із прогонами бота

Крон пише в `data/` і `store/` щогодини. Якщо ти теж щось ганяв локально, при
`git pull` буде конфлікт — це норма, а не аварія.

**Не знімай його через `git checkout --ours` чи `--theirs`.** Обидві сторони
містять пости, яких нема в іншої, і вибір однієї знищує решту назавжди:
`t.me/s/` віддає обмежену глибину історії. Втрата мовчазна — файл валідний,
конвеєр працює, подій просто нема.

Замість цього один раз у клоні:

```bash
python3 mergejsonl.py --install
```

Далі `git pull` просто працює: сирі пости обʼєднуються за `id`, події за `id`
зі збереженням часового порядку, курсори в `state.json` беруться максимальні.

`git clone` цього НЕ переносить — `.gitattributes` їде з репозиторієм, а сам
драйвер живе в локальному `.git/config`. Доки не ввімкнено, Git конфліктує як
завжди, тобто мовчазної втрати не буде в жодному разі.

Після злиття похідний шар варто вирівняти: `python3 sync.py --rebuild`.

## Локальний запуск

```bash
pip3 install -r requirements.txt
python3 sync.py --rebuild        # зібрати сховище з наявного кешу
python3 site.py --raids          # згенерувати сайт
python3 -m http.server -d site 8000
```
